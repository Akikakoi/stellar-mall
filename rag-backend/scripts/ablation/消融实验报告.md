日期：2026-11-05 ｜ 环境：本机 Docker（ES 8.13 + Redis 7.2 @6380）+ 本机 MySQL + stellar-server(8082) + rag-backend（DashScope text-embedding-v2 / DeepSeek deepseek-chat / BGE reranker-v2-m3 CPU）

## 0. 实验设置

- 评测集：40 条 query（`eval_set.json`），手写、标注文档级相关性，四类各 10 条：
  - **exact** 精确词面（含确切型号/参数词）— BM25 理论强项
  - **semantic** 语义改写（同义换说法，不含文档原词）— 向量理论强项
  - **multi_constraint** 多约束组合（电池+快充、屏幕+独显等）
  - **multi_turn** 多轮指代（带上文 context，追问含"它/那款/这款"）
- 检索指标（文档级，去重）：Recall@12、MRR、nDCG@5、延迟
- 端到端：完整 Agent 链路（意图分类 → 工具 → 答案生成），DeepSeek LLM-as-judge 0-5 分
- 指标口径说明：各变体顺序执行，embedding LRU 使后执行变体的 embed 耗时接近 0，对比延迟时以各阶段分量为准（单次 embedding 约 1.2s，均摊到 vector/rrf/rerank 三组相当）

## 1. 检索链路消融（40 条，文档级）

| 变体 | recall@12 | MRR | nDCG@5 | P50 延迟 | 说明 |
|---|---|---|---|---|---|
| bm25_only | **0.871** | 0.536 | 0.696 | 13ms | 关键词面最强，语义最弱 |
| vector_only | 0.757 | 0.421 | 0.584 | ~1.2s(+embed) | 语义最强（1.000），多约束崩（0.578） |
| rrf_hybrid | 0.854 | 0.532 | 0.676 | ~17ms(+embed) | 取长补短，但 MRR 未超 BM25 |
| rrf_hybrid_rerank | 0.854 | **0.729** | **0.855** | +9s(CPU) | **排序质量主力**，recall 不变 |

分类型 recall@12：

| 变体 | exact | semantic | multi_constraint | multi_turn |
|---|---|---|---|---|
| bm25_only | **1.000** | 0.800 | **0.885** | 0.800 |
| vector_only | 0.850 | **1.000** | 0.578 | 0.600 |
| rrf_hybrid | 1.000 | 0.900 | 0.815 | 0.700 |
| rrf_hybrid_rerank | 1.000 | 0.900 | 0.815 | 0.700 |

**结论**
1. **Rerank 是排序质量主力**：recall 不变（0.854），但 MRR +37%（0.532→0.729）、nDCG@5 +26%（0.676→0.855）——它把正确文档顶到了前排，直接决定 LLM 能不能看到对的上下文。
2. **RRF 混合的价值在补短板**：exact 由 BM25 拉满 1.000，semantic 由向量补到 0.900，多约束场景两者都一般（0.815/0.578）——数值型约束（"3000nit 以上""16GB 内存"）是当前检索的明显短板。
3. **CPU Reranker 是延迟大头**：12 条候选精排 ~9s，占端到端延迟 80%+。精排候选数（RETRIEVER_TOP_K=12→6）或换 GPU/ONNX 是最大优化杠杆。

## 2. Query Rewrite（指代消解）消融（10 条多轮）

| 变体 | recall@12 | MRR | nDCG@5 | 说明 |
|---|---|---|---|---|
| raw（rewrite 关） | 0.700 | 0.500 | 0.539 | 追问原样检索 |
| rewrite_on（LLM 改写） | 0.900 | 0.696 | 0.992 | 改写成本 ~1s LLM 调用 |
| oracle（人工自包含上界） | 1.000 | 0.746 | 1.035 | 改写质量已接近上界 |

**结论**
1. 指代消解对多轮场景收益显著：nDCG@5 **+84%**（0.539→0.992），recall +0.20；LLM 改写结果已接近人工上界（D03"屏幕最大那款"改写后反而变宽导致丢失，是唯一倒退项）。
2. 注意：线上触发正则只匹配"它/他的/她的/该款/此款"，本次 10 条中仅 3 条会被生产规则真正触发——**"这款/那款/这台/这个版本"等高频指代词不在触发范围**，是明确的可改进点。
3. 改写带三层缓存，重复多轮会话命中缓存时改写近零成本。

## 3. LLM 三层缓存消融（12 条产品咨询，完整 Agent 链路）

| 阶段 | 延迟avg | L1 命中 | L2 命中 | miss | 命中率 |
|---|---|---|---|---|---|
| P0 全关（基线） | 8674ms | 0 | 0 | 0 | 0 |
| P0b 冷启动写入 | 6107ms | 0 | 0 | 18 | 0 |
| P1 L1 精确重放 | **3503ms** | **18** | 0 | 0 | **100%** |
| P2 L2 语义（同义改写） | 4704ms | 0 | 6 | 16 | 27.3% |
| P2b 关 L2 重放 | **1428ms** | 17 | 0 | 0 | 100%（L1 回写） |
| P3 全新 query | 11634ms | 0 | 0 | 12 | 0 |
| P4 single-flight（6 线程） | - | producer 调用 **1 次** ✓ | | | |

**结论**
1. **L1 精确缓存收益确定**：完全重复 query 命中 100%，端到端 -60%（8674→3503ms），剩余延迟来自 kb_search + CPU Rerank（缓存不覆盖工具层）。
2. **L2 语义缓存覆盖面有限**：0.90 rerank 阈值下 12 条同义改写只接住 6 条（27%）——只接得住礼貌语/标点级近重复，真实换说法接不住（与 config 注释的 embedding 观测一致：真改写 ~0.78，近重复 ~0.94）。**提高覆盖要么降阈值（风险：跨意图误命中），要么先做轻量归一化**。
3. **L2→L1 回写机制有效**：语义命中后回写 L1，同 query 第二次 1428ms 直达 L1。
4. **single-flight 防击穿有效**：6 线程并发同一冷 query，producer 仅 1 次真实调用。
5. 附带发现：`get_sync` 同步路径不检查 `LLM_CACHE_SEMANTIC_ENABLED`，**在 Agent 链路上关 L2 的配置开关是无效的**（本次用 monkeypatch 消融）；L1 客户端依赖 FastAPI lifespan 注入，独立脚本/工具直调时必须手动 `init_redis()`。

## 4. Agent 端到端消融（LLM-as-judge 0-5 分，缓存全程关闭）

| 组 | 变体 | n | 平均分 | 延迟avg |
|---|---|---|---|---|
| R 单轮 | full（Rerank 开） | 8 | 3.75 | 10.4s |
| R 单轮 | no_rerank | 8 | 3.88 | 6.6s |
| D 多轮 | full（Rewrite 开） | 10 | 2.60 | 12.3s |
| D 多轮 | no_rewrite | 10 | 2.30 | 8.3s |

**结论**
1. **Rerank 在端到端质量上未体现增益**（3.75 vs 3.88，样本 8 条在噪声范围内），却贡献 +3.8s 延迟——与第 1 节"rerank 显著改善检索排序"并不矛盾：top-12 候选集相同，多数 query 的候选已足够好。**结合 1+4：rerank 的真正价值在 nDCG/MRR（上下文排序），若要省延迟可评估"rerank 只在候选分数接近时介入"或降候选数**。
2. **Rewrite 端到端 +0.3 分、+4s**：典型改善如 D03（关改写直接空回答），但 D02/D09 两个变体都答错——失败根因不在改写。
3. **独立的失败模式（与消融变量无关，值得单独立项修）**：
   - D02/D09：意图分类把追问路由错商品（把"玉米手机 10 Pro 的续航"答成星耀 A60、把 Note 14 Pro 价格答成 Flip 折叠屏）——多轮实体绑定在意图/参数节点丢失；
   - B06/C03：KB 明确有答案但回答"无法确认"——检索到了但工具上下文组装/置信度判断保守。

## 5. 建议优先级

1. **修多轮商品实体绑定**（D02/D09，端到端最大失分点）
2. **扩大指代触发正则**（这款/那款/这台/这个版本，改写有缓存、边际成本低）
3. **Rerank 延迟优化**（候选 12→6 或 GPU/ONNX；CPU 上省 ~4.5s/次）
4. **L2 语义缓存阈值策略**（维持 0.92/0.90 现状，或加 query 归一化前置；不建议直接降阈值）
5. 多约束数值检索（"3000nit 以上"类）可考虑在 KB 文档中补结构化参数表提升 BM25 词面命中

## 7. 局限性

- 样本量小（40/10/12/8-10 条），单项差异 <0.3 分或 <0.1 指标应视为噪声；
- LLM-as-judge 单次判分，未做多次采样一致性校验；
- 延迟受本机 CPU Reranker 与 embedding LRU 影响，绝对值仅本机参考；
- 评测集为人工构造，标注主观性无法完全排除；线上真实 query 分布（尤其订单/售后类工具调用）未覆盖；
- **e2e harness 直调 run_agent，`other` 意图（生产走 ReAct）会得到空回答**，凡判 other 的案例生产实际表现优于本报告 e2e 分数。

- 使用 DeepSeek deepseek-chat（temperature=0.3）、DashScope text-embedding-v2、CPU bge-reranker-v2-m3。检索与改写的知识库均为 266 片段，内容指纹一致：`1309cc409c09b418873345ee3c169a4d409269885ea5ad56cbe38feda7adef6e`。

- 精排使用真实 BGE，失败不会用余弦排序冒充成功；关闭精排时替换实际调用绑定，而非仅改配置。模型预热不计入响应延迟。
- 检索、改写每次清除相应 query 的 embedding LRU，随机变体顺序；Agent 绕过 LLM、FAQ、embedding 和文档进程缓存。不同实验之间延迟口径不同，不横向相减。
- 下述 95% 区间为配对问题 bootstrap：先在同题内平均两轮差值，再按独立问题有放回抽样 5,000 次（seed=20261107）。重复轮不是新增独立样本；区间只描述该人工题集上的不确定性。

每个变体 40 个独立问题、80 次观测，表中为两轮平均；延迟包含冷 query embedding、ES 和已预热 BGE，不含 HTTP。

| 变体 | 文档召回 | MRR | nDCG@5 | 平均延迟 |
|---|---:|---:|---:|---:|
| BM25 | 0.8163 | 0.5473 | 0.5671 | 8.5 ms |
| 向量 | 0.7071 | 0.4142 | 0.4233 | 494.3 ms |
| RRF 混合 | 0.8163 | 0.5305 | 0.5223 | 520.2 ms |

| P2 L2 开（同义改写） | 6,098 ms | 0/0 | **0/6** | 20 | 仅意图层命中 6/12 |

| P3 全新 query | 12,776 ms | 0/0 | 0/0 | 12 | 独立空目标，不是热缓存新 query 测试 |

- **L1 精确缓存收益明确**：原 query 重放时答案与意图各 12 次全部命中，观测平均延迟从 8.4 s 降至 3.4 s；这是单轮观测，不能把全部差值都归因于缓存，但机制确实被真实调用。
- **L2 答案缓存 0 命中是实质结果**：12 条同义改写都执行了答案层 L2 查询，全部 miss；6 次命中均在意图层。因此本次没有证据表明 L2 答案缓存能接住同义改写，也不能用“L2 命中 6 次”宣称答案缓存 27% 覆盖。
- **原因可定位**：答案层语义检索会过滤 `context_hash`，而该值是本次 `tool_result`（含来源、分数、内容）的 SHA256。12 条改写中 11 条检索上下文与 seed 不同，在相似度比较前即被排除；唯一同 `context_hash` 的一条余弦相似度 0.8301，低于 0.90 阈值。另有 6 条改写余弦相似度超过 0.90，但因 `context_hash` 不同仍不会命中。**当前设计下，工具上下文变化会先于阈值阻断答案级语义复用。**
- P2 与 P2b 的延迟差（约 -382 ms）只对应 6 次意图缓存命中，不能解释为答案缓存收益。
- single-flight 单元探针：开启时 6 个 worker 仅 1 次 producer 调用、5 个等待者；关闭时 6 次调用、0 等待者。该探针使用真实算法与合成 producer，不代表 HTTP/API 吞吐。

旧报告“L2 命中 6 次（27%）”来自全局 `l2_hits` 计数，未区分答案与意图；本次分层观测表明那 6 次是意图层命中，不能沿用为答案缓存结论。

### 10.3 为什么仍是 0 命中

对 v2 的 12 对改写按“同一问题的原句↔改写”重新配对后：

- 相似度 ≥ 0.90 的有 **6/12**（第 1、2、6、7、8、11 条），但它们的 `tool_result` 证据都不同；
- 证据完全相同的有 **1/12**（第 10 条），但相似度只有 **0.8301**；
- 同时满足“证据相同 + 相似度 ≥ 0.90”的有 **0/12**。

v3 的 3 题中，第 3 题证据相同但相似度 0.8912；第 1、2 题相似度 0.9251/0.9387 但证据不同。两种运行都得到同一结论：**没有一条改写同时满足当前安全条件**。因此不能把本次修复描述为“已解决 L2 答案缓存覆盖”，只能描述为“移除了一个过严的上下文过滤”。

### 10.4 处理决定（2026-11-07）

**保留本次证据指纹修复，不调整 0.90 阈值。** 理由：

- 本次改动只去掉分数、顺序、问句文本这类非语义差异；证据集合不同时仍拒绝复用，属于收紧边界而非放宽安全条件。
- 本数据集中“证据相同 + 相似度 ≥ 0.90”为 0/12，说明阈值是当前真正的限制；在未加否定词守卫前，降低阈值会把“支持/不支持”这类高相似问句带入复用，风险大于收益。
- 若后续确实要提升同义改写覆盖，优先评估“工具执行前静态 KB 查询缓存”，而不是继续下调阈值；价格、库存、订单等实时工具不进入该缓存。

验证产物保留为 `results_cache_20261107_v3_limit3c.json`；该文件只覆盖前 3 题，不替代 v2 的 12 题基线。
