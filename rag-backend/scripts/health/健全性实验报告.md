# 项目健全性实验报告（故障注入 / 意图混淆矩阵 / 安全扫描）

日期：2026-11-05 ｜ 环境：本机 Docker（ES 8.13 + Redis 7.2@6380）+ 本机 MySQL + stellar-server(8082) + DeepSeek deepseek-chat
脚本：`rag-backend/scripts/health/`（fault_injection.py / intent_matrix.py / security_scan.py，均不改动源码）

## 实验 1：故障注入 / 降级验证 —— 9/10 通过

| 场景 | 检查项 | 结果 |
|---|---|---|
| S1 停 ES | 搜索 /user/spu/page 降级 MySQL | ✅ 200 + 数据，783ms（快失败不阻塞） |
| S1 停 ES | 搜索建议 /user/spu/suggest（ES 专用） | ✅ 200 + 空结果，优雅降级 |
| S1 停 ES | ES 恢复后搜索 | ✅ 200 |
| S2 停 Redis | 限流拦截器 | ✅ 降级放行（可用性优先，符合设计） |
| S2 停 Redis | JWT 黑名单校验 | ✅ 降级放行（签名/过期校验兜底） |
| S2 停 Redis | **登录接口** | ❌ **HTTP 500"系统繁忙"——发现真实缺陷** |
| S2 停 Redis | Redis 恢复后 | ✅ 200 |
| S3 Mall API 不可达 | 熔断器第 6 次调用 fail-fast | ✅ 熔断打开，报"预计 30s 后恢复" |
| S3 Mall API 不可达 | fail-fast 生效（总耗时 41s << 5×超时=50s） | ✅ |
| S3 Mall API 不可达 | 30s 恢复窗口后调用真实地址 | ✅ 放行且成功，熔断闭合 |

**发现 1（缺陷）：Redis 不可用时登录接口 500 无降级。** 疑似登录链路（验证码/记录/会话写入）强依赖 Redis，未做 try-catch 降级。建议定位 UserController.login → Service 链路上的 Redis 写点并加降级。
> **✅ 已修复（2026-11-06）**：`LoginAttemptServiceImpl` 四个 Redis 调用（checkLocked/recordFailure/clearAttempts/unlock）全部补 `DataAccessException` 降级（放行/跳过 + warn 日志，与限流拦截器口径一致）；`MallUserServiceImpl.issueTokens` 的单设备 refresh 覆盖写同样降级（Redis 离线期间旧 refresh 不被顶下线）。实测：停 Redis 后登录（错密码）返回 HTTP 200 + 业务码 40101，不再 500；恢复后正常。309 个单元测试全过。代价说明：Redis 离线期间暴力破解锁定防护暂时失效，由 JWT 签名校验与接口限流兜底。

**发现 2（质量）：ES 降级后召回质量缩水。** 停 ES 搜"手机"仅命中 1 条（MySQL LIKE 只匹配品名字面），而 ES 混合检索会返回数十条语义+关键词结果。降级"可用"但"不好用"，符合预期设计，可考虑 fallback 补充分类/标签匹配。

## 实验 2：意图分类混淆矩阵 —— 整体准确率 98.8%

- 16 类意图 × 10 条 = 160 条，DeepSeek 直判（绕过缓存），4 线程并发，平均延迟 1468ms
- 14/16 类 100%；wallet_query、review_query 各 1 条被判 other（"帮我看下账户里有多少钱" / "看看购物评价"这类短句偏模糊）
- 规则快路径命中 28/160（显式指令类 query 免 LLM）
- **Top 混淆仅 2 对且都滑向 other**（保守策略，宁可进 ReAct 也不错判），无跨意图误判
- 结论：意图分类层健康，160 条评测集可直接作为后续改 prompt/换模型的回归基线

## 实验 4：权限与安全扫描 —— 12/12 通过

| 组 | 检查项 | 结果 |
|---|---|---|
| A JWT 变造 | 无 token / 过期 / 错误密钥 / 篡改签名 | ✅ 全部 401 |
| A JWT 变造 | 合法签名但非资源属主 | ✅ 业务拒绝"无权限"不泄露数据 |
| B 水平越权 | 用户 4 → 用户 6 的订单/地址（读 + 删） | ✅ 全部拒绝（"无权限/不存在"，data:null） |
| B 水平越权 | 阳性对照（属主访问自己资源） | ✅ 200 正常 |
| B 水平越权 | 用户 4 订单列表不含他人订单 | ✅ 列表为空 |
| C 限流 | /user/user/login 10/min，连打 15 次 | ✅ 200×10 + 429×5（滑动窗口精确生效） |

说明：项目的拒绝语义是 HTTP 200 + `code:0` 业务码（非 HTTP 4xx），判定口径已按实际契约校准。限流第二轮连打全 429 为上轮耗尽 60s 滑窗的延续，两轮合并恰好验证 10/min 配置。

## 总体结论

- **基础设施降级设计基本健康**：ES fallback、限流降级、黑名单降级、熔断器生命周期全部按设计工作
- **1 个待修缺陷**：Redis 不可用时登录 500（唯一红项）
- **意图分类层 98.8%**，无跨意图混淆，评测集沉淀为回归基线
- **安全面干净**：JWT 校验、所有权校验、限流全部有效
