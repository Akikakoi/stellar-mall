# 双后端边界契约

> P3 收敛评估（2026-10-30）的落地文档。结论：双后端是刻意的架构分工而非技术债——
> 商城业务复杂度（16.8k 行 Java）与 AI 复杂度（9.6k 行 Python + LangChain 生态）
> 天然分属两个技术栈，所有耦合收敛到本文所列的显式契约通道。
> **演进规则：改动任何一条通道的端点 / 鉴权 / 超时 / 失败语义，必须同步更新本文。**

## 架构总览

| | Java 商城后端（stellar-server） | Python RAG 后端（rag-backend） |
|---|---|---|
| 端口 | 8082 | 8000（API 前缀 `/api`） |
| 职责 | 商城全业务、ES 商品搜索、管理后台 | RAG 问答、Agent、知识库、ChatBI、embedding、MCP |
| 自有数据 | MySQL `stellar_*` 表 | MySQL `stellar_rag_*` 表（P3-2 起） |
| 技术栈 | Spring Boot 3 / jjwt / spring-data-es | FastAPI / LangChain 1.x / FlagEmbedding |

四个服务边界：前端 `userRequest/adminRequest` → Java，`ragRequest`（`/ragapi`）→ Python。

## 通道 1：Embedding 服务（Java → Python）

| 项 | 契约 |
|---|---|
| 端点 | `POST {rag.base-url}/api/embed` |
| 鉴权 | 无（限内网/本机） |
| 超时 | connect 5s / read 60s |
| 批量 | 单批最多 50 条（服务端字段上限 100，保守取 50） |
| 代码 | Java [SpuEsSyncService.java](../stellar-server/src/main/java/com/stellar/elasticsearch/sync/SpuEsSyncService.java) / Python `app/api/embed.py` |

**失败语义**：分批调用，单批失败只影响该批（槽位置 null，不阻断全量同步）；
向量维度不符同样丢弃。降级后该 SPU **退化为纯关键词搜索**（keyword-only），
不阻塞商城主流程。

**一致性约束**：`stellar.elasticsearch.vector-dim`（默认 1536）必须与
rag-backend 的 embedding 模型输出维度一致（DashScope text-embedding-v2 = 1536）。
更换模型时：两端配置同步改 + `stellar_spu` / `stellar_kb_chunks` 两个索引都要 rebuild。

## 通道 2：数据同步（Java → Python，共享密钥）

| 项 | 契约 |
|---|---|
| 端点 | `POST /api/internal/sync_spu`（SPU 新增/更新/上下架）、`/api/internal/sync_doc`（政策/公告/优惠券规则）、`/api/internal/daily_report`（AI 经营日报） |
| 鉴权 | Header `X-Stellar-Rag-Sync-Secret`，两端常量时间比对（防时序攻击）；密钥配置：Java `stellar.rag.internal-sync-secret` / Python `STELLAR_RAG_INTERNAL_SYNC_SECRET`，**必须 100% 一致** |
| 超时 | 同步类 `RagSyncProperties.timeoutMs=10s`；LLM 类（daily_report）`reportTimeoutMs=90s` |
| 代码 | Java `ragsync/client/impl/DefaultRagSyncClient.java` / Python `app/api/internal.py` |

**失败语义**：非 2xx 或 IO 异常抛 RuntimeException。SPU 变更事件经异步执行器触发
同步，失败只记日志，不影响商城保存主流程；幂等设计（先按 `source+biz_id+biz_type`
删旧分块再写入），可通过再次触发同步或全量 rebuild 兜底。
同步成功后 Python 侧自动精准失效 L2 语义缓存（按 spu_id）与 kb_tool 全量文档缓存。

## 通道 3：ChatBI 中转（Java ↔ Python）

```
前端 /admin/chatbi/query（180s 超时）
  → Java ChatBiService：组装问题+受控表结构
    → Python /api/internal/chat_bi/sql（90s）→ LLM 生成 SELECT + 图表配置
  → Java 本地安全校验（LLM 输出不可信）：
      单条 SELECT / 无分号多语句 / 表名白名单 / 敏感列黑名单 / 自动补 LIMIT / 执行超时 10s
  → Java JdbcTemplate 执行（限行数）
    → Python /api/internal/chat_bi/summary（90s）→ LLM 生成自然语言总结
  → Java 返回前端
```

**设计约束**：前端**不直连** Python——Java 的 SQL 白名单安全层是本通道的核心价值，
两跳中转是有意为之，勿"优化"掉。鉴权同通道 2（共享密钥）。

## 通道 4：Agent 工具调用（Python → Java）

| 项 | 契约 |
|---|---|
| 端点 | `/user/spu/page`、`/user/cart`、`/user/order/*`、`/user/review/spu/{id}`、收藏/钱包等 C 端只读与受限写接口 |
| 鉴权 | 透传用户 mall_token（Java 签发的 JWT） |
| 超时/重试 | `MALL_API_TIMEOUT_SECONDS=10`、`MALL_API_MAX_RETRIES=2` |
| 熔断 | 连续 5 次失败打开，30s 后半开恢复 |
| 代码 | Python `app/agent/tools/mall_client.py`（统一封装 `call_mall`） |

**失败语义**：重试穷尽后返回统一错误形态 `{success: false, message: 友好提示}`，
Agent 据此引导用户稍后再试；熔断打开时快速失败，不产生请求堆积。
写操作（加购/改购物车）经 `react_safety.safe_invoke` 强制参数来源白名单
（sourced_ids）+ 幂等守卫，高危写（取消订单/售后/清空）不注入 ReAct 工具集。

## 横切：JWT 三段式互通（单向 SSO）

- Java（jjwt，HS256，UTF-8 raw bytes）签发管理端 `STELLAR_ADMIN_SECRET_KEY`
  与 C 端 `STELLAR_USER_SECRET_KEY` 两种 token。
- Python `decode_token` 依次尝试：RAG 自有 `SECRET_KEY` → ADMIN key → USER key，
  任一成功即放行（[security.py](../rag-backend/app/core/security.py)）。
- 方向为 **Java 签发 → Python 解析**（单向）；Python 自签 token 仅 RAG 内部使用。
- Mall token 首次访问 RAG 时创建影子用户（`stellar_rag_users`）以支持外键关联。

## 共享基础设施分治

| 设施 | Java 侧 | Python 侧 |
|---|---|---|
| ES :9200（xpack 关闭） | 索引 `stellar_spu`（商品 kNN 搜索） | 索引 `stellar_kb_chunks`（知识库）、`stellar_llm_cache`（L2 语义缓存） |
| MySQL stellar_mall 库 | 业务表 `stellar_*` | RAG 表 `stellar_rag_*`（P3-2 迁入） |
| Redis | db0：业务缓存/延迟队列/分布式锁 | db11：LLM 三层缓存、suggestion |

**注意**：ES 的 `rank.rrf` 需白金 license（Basic 403），Python 侧混合检索用
双查询 + 应用层 RRF 融合替代；两端 kNN 均为 dense_vector 1536 cosine。

## 边界变更守则

1. 改任何通道的端点 / 密钥 / 超时 → 同步修改两侧配置并更新本文
2. 改 ES mapping → 对应索引需 delete + rebuild（`POST /admin/es/rebuild`）
3. 换 embedding 模型 → 两端维度配置同步 + `stellar_spu` 与 `stellar_kb_chunks` 全部 rebuild
4. 新增跨端能力 → 先在本文登记契约（方向/端点/鉴权/超时/失败语义），再写代码
